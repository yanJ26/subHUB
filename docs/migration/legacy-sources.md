# 旧项目迁移规范

## 固定基线

- apiHUB：`9cb76534d628e4dbbbbaac5b3312c81440f6d361`
- agentHUB：`8a4ed37`
- buddyHUB：`5803521`

## 权威规则

- 现有 subHUB 数据始终作为导入基线，迁移只做合并，不会先清空工作区。
- 价格、币种、计费周期、续费日、渠道、提醒、标签和发票：来自 apiHUB 的记录作为旧项目首选来源。
- Agent、设备、部署、访问入口、Runtime、版本和安装方式：来自 agentHUB 的记录作为旧项目首选来源。
- 额度快照、人工评价和工作记录：来自 buddyHUB 的非重复记录参与合并；没有商业信息的 Agent 不生成虚构权益。
- 真实凭据：全部拒绝迁移；subHUB 只保留非敏感的凭据标签，真实凭据继续由对应服务的专用密钥存储管理。

## 迁移步骤

1. 从三个旧系统分别导出 JSON，并在系统外生成校验值。
2. 在 subHUB 选择文件，只生成预览。
3. 核对统计、警告、孤立关系，以及现有 subHUB 数据与导入数据之间的重复权益。
4. 对每个阻塞冲突显式选择“保留两条”“保留现有/优先来源”或“采用新导入记录”；未处理完全部冲突不能提交。
5. 提交绑定文件摘要、预览令牌和数据库修订号；文件或工作区任一变化都必须重新预览。
6. 每条旧记录写入 `legacy_refs`，保存来源系统、实体类型、旧 ID、目标 ID 和内容哈希。
7. 导入后核对费用合计、30 天内事件、发票、标签、设备、部署和入口数量。

导入只写 subHUB。三个旧仓库和旧数据库不会被修改。
